# 代码审查规范

> 对仓库最新 commit 进行系统化审查，输出标准化报告至 `cr_reports/{commit_short_hash}.md`。

---

## 审查流程

```bash
# 1. 获取变更
git log -1 --pretty=format:"%h %s"
git diff --stat HEAD~1 HEAD
git diff HEAD~1 HEAD

# 2. 按下方模板逐项审查，输出报告
# 3. 报告保存至 cr_reports/{commit_short_hash}.md
```

---

## 审查重点（按变更类型调整优先级）

| 变更类型 | 审查重点排序 |
|---------|-------------|
| 🆕 新功能 | 功能正确性 → 设计合理性 → 代码质量 → 影响评估 |
| 🐛 缺陷修复 | 根因分析 → 修复完整性 → 回归风险 → 测试覆盖 |
| ♻️ 重构 | 行为保持 → 设计改进 → 向后兼容 → 测试保持 |
| ⚡ 性能优化 | 性能验证 → 正确性保证 → 资源影响 → 可观测性 |

---

## 易遗漏的审查要点

每次审查必须主动检查以下问题：

- **隐式行为变更**：函数签名没变但内部行为/副作用/返回语义变了，调用方未同步更新
- **部分修复**：bug fix 只修了一个入口，同一逻辑的其他入口仍有问题
- **错误路径遗漏**：只审查 happy path，未验证异常/超时/空值/并发下的行为
- **跨文件一致性**：改了数据结构但没更新序列化/反序列化/文档/测试
- **默认值与零值陷阱**：新增字段的默认值对已有数据是否安全
- **日志/监控盲区**：新增关键路径但没有对应的日志、指标、告警

---

## 关键原则

1. **分析"为什么"而非描述"是什么"**——不要复述代码做了什么，要分析为什么这样做、是否有更好的方式
2. **每个问题必须给出可执行的修改建议**——包含具体代码 diff，而非泛泛建议
3. **主动检查变更未涉及但应该同步修改的地方**——测试、文档、关联模块

## 报告模板

````markdown
# 代码审查报告 - {commit_short_hash}

## 📋 摘要

| 项目 | 内容 |
|------|------|
| 提交信息 | `{commit message}` |
| 变更类型 | 🆕新功能 / 🐛修复 / ♻️重构 / ⚡性能 / 📝文档 |
| 变更规模 | 修改 X 文件，+Y / -Z 行 |
| 影响范围 | 🟢局部 / 🟡模块级 / 🔴系统级 |
| 风险评级 | 🟢低 / 🟡中 / 🔴高 |
| 建议操作 | ✅可合并 / ⚠️小幅修改后合并 / ❌需重大修改 |

**核心变更**：
1. 变更点 1 — 目的与实现方式
2. 变更点 2 — 目的与实现方式
3. 变更点 3 — 目的与实现方式

---

## 🔍 逐项审查

### 功能正确性
- 业务逻辑是否完整实现
- 边界条件与异常路径
- 数据一致性保证

### 代码质量
- 可读性与命名
- 错误处理完整性
- 资源管理（泄漏风险）
- 并发安全

### 设计与架构
- 与现有架构一致性
- 模块职责与耦合度
- 接口设计与向后兼容

### 影响与风险
- 直接/间接影响范围
- 性能、稳定性、安全风险
- 可观测性（日志/监控/告警）

---

## 🔧 改进建议

### 必须修复（阻塞合并）
1. **问题描述**
   ```diff
   - 问题代码
   + 建议修改
   ```

### 建议改进
1. 改进点及理由

### 风险提示
1. 风险描述及规避建议

---

## 🎯 总体评价

| 维度 | 评级 |
|------|------|
| 代码质量 | 🌟优秀 / 👍良好 / ⚠️需改进 |
| 设计水平 | 🌟优秀 / 👍良好 / ⚠️需改进 |
| 可维护性 | 🟢高 / 🟡中 / 🔴低 |
| 测试完整性 | ✅完整 / ⚠️部分 / ❌缺失 |
````
